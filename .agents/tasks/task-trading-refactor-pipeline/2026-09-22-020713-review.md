# Trading Ubin & Material Alam handoff — end-to-end pipeline, funnels, dual-view, SJ cross-check (v1)

The change lands the Trading handoff across five sections on the classic IIFE layer: a weighbridge-driven purchase pipeline (PO → Surat Jalan/Timbangan → Rekonsiliasi → Multi-Invoice → Payment) in a new `pipeline-extras.js`; dashboard purchase/sales funnels plus a custom-range report in `funnel-report.js`; a supplier Surat-Jalan cross-check engine in `sj-validation.js` that flags tonnage/price overstatement before invoicing; an RBAC "surface" layer with an Entri Harian data-entry view for Admin/Accounting vs an executive dashboard for Owner/Management; and a senior-friendly type/contrast pass on the CSS. GL stays derived — the pipeline creates purchase-invoice documents and lets `gl-sync.js` post journals; no journals are hand-written. Section 4 (Coretax export) and Section 2 live email ingestion are deliberately deferred to a documented field-mapping note and a pluggable recap-source contract respectively.

Watch for: the funnel "Cocok" (matched) dashboard stat counts mismatched rows as matched, understating the problem count it is meant to surface (confirmed, UI-only); the `crossCheck` matched/mismatched summary semantics overlap (unmatched-field rows count as `mismatch` but not `matched`), which is coherent in the engine but drives the misleading UI stat (confirmed); the sales-funnel "Pengambilan Bertahap" stage counts any delivery order lacking a `poId` as a sales pickup, which can misattribute purchase-side DOs written without a `poId` (likely). Build, lint, and 269 tests are green; type-check shows only the 12 known pre-existing baseline errors.

**Verdict**: APPROVED

## High-level view

The pipeline is built around a small set of pure functions in `pipeline-extras.js` — `computeWeighing`, `computeVariance`, `invoiceBasisQty`, `buildInvoiceLinesFromReceipt` — that make netto always derived (gross − tare) and make the reconciled quantity, not the ordered quantity, the invoice basis. The DOM views (reconciliation grid, multi-invoice button) sit on top and are thin. Invoices are plain `purchaseInvoices` documents, so the existing derived-GL path posts the journals unchanged; the reconciliation test proves the resulting PI produces a balanced journal via `GL.buildPIJournals`.

The SJ cross-check engine (`crossCheck`) is a pure matcher keyed on PO/DO number + item name, with a dual absolute-or-percentage tolerance band that must be breached on both axes to flag. The rough edge is on the presentation side: the summary counts and the dashboard "Cocok" stat conflate matched-with-mismatch rows, so a demo where one of two matched rows is flagged still reports two as matched.

Funnel counting in `funnel-report.js` derives the exact handoff stage labels from DB collection states. The purchase funnel is precise; the sales funnel's pickup stage uses a permissive "no poId ⇒ sales" fallback that can miscount DOs whose PO link was stored under a different field.

The RBAC change layers `ROLE_SURFACES`/`surfaceFor`/`canViewSurface` on top of the existing permission matrix as UI composition only — every mutation is still gated by `can()`/the saveDB net and firestore.rules, so the trust boundary is unchanged. Entri Harian re-uses existing create handlers by synthesizing clicks rather than duplicating logic. The classic-bundle wiring registers all four new files in `classicAll` ahead of `menu-router.js`/`rbac.js`, matching the dependency order the layer requires.

Deferred scope is handled as specified: Section 2 email ingestion is a `registerRecapSource` adapter contract with a working upload source and a documented mailbox example; Section 4 Coretax is a readiness comment over the existing VAT-invoice structure with no serializer.

### Reconciled quantity as the invoice basis

`computeWeighing` recomputes `netQty = gross − tare` and refuses a supplied `netQty` whenever a gross reading exists — the scale is the source of truth, not a typed-in number (the test passes a bogus `netQty: 999` against gross 40 / tare 10 and asserts 30). `invoiceBasisQty` walks reconciledQty → weighed netto → surat-jalan qty → ordered qty. The reconciliation test feeds the produced PI to `GL.buildPIJournals` and asserts `debit === credit`, proving the derived-GL invariant holds through the new path; the multi-invoice test stages two receipts against one PO and pins the DO transition `Partially invoiced` → `Invoiced` and the reconciledQty basis (28 vs ordered 30), so a reversion to ordered-qty invoicing or dropped status updates would fail.

One asymmetry between the pure helper and the UI: `computeWeighing` supports a single-netto capture (no gross), but the receive-modal save path in `sales-purchase-extras.js` uses `net = gross > 0 ? Math.max(0, gross - tare) : 0`. An operator who enters only a netto (common when a supplier weighbridge ticket is trusted for one leg) persists `netQty: 0`, and `invoiceBasisQty` then silently falls back to the surat-jalan or ordered qty rather than the intended netto. The reconciliation modal can correct it later, but the first-capture value is lost.

### SJ cross-check engine and tolerance

`beyondTolerance` passes when a variance is within *either* the absolute *or* the percentage band and only flags when it breaches *both*, absorbing rounding noise on small quantities while still catching the demo's +3t / +Rp15k overstatement. Keying on item *name* (with code/id as fallback) is right for supplier recaps that don't carry internal item codes. The suite exercises tonnage-only, price-only, both, within-tolerance, custom looser tolerance, DO-number matching, and both unmatched directions — a reversion of the flagging logic would fail several of these.

The summary semantics are where it gets subtle. `matched` counts rows with `matched === true`; `mismatched` counts rows with `mismatch === true`, and an unmatched *field* row is emitted with `matched: false, mismatch: true`. So `mismatched` spans two conditions (a matched row over tolerance, and a field line with no recap counterpart), and `matched` and `mismatched` are not disjoint — a matched row over tolerance is in both. Consistent for the engine, but it makes the summary unsafe to render naively.

```js
// _renderResult, "Cocok" stat:
{ label: 'Cocok', value: String(s.matched - s.mismatched < 0 ? 0 : s.matched), ... }
```

The ternary computes `s.matched - s.mismatched` only to decide between `0` and `s.matched` — the subtracted value is never shown, so the stat displays the full matched count including rows that are flagged. In the seeded demo (two matched rows, one flagged) the widget reports "Cocok: 2" next to "Bermasalah: 1", which undercounts the clean rows and overstates safety on exactly the screen meant to stop a bad invoice. The fix is to show clean = matched − (matched rows carrying a mismatch), which argues for the engine exposing a `clean` count rather than each caller re-deriving it.

### Funnel stage counting

The stage labels match the handoff exactly. The sales funnel's "Pengambilan Bertahap" stage counts a DO as a sales pickup when it has `soId`/`soNumber`/`source==='SO'` *or* has neither `poId` nor `poNumber`. That trailing negative clause means a purchase-side DO recorded without a `poId` (for instance linked only through `sourceId`, which the pipeline's `updatePODeliveryInvoiceStatus` does read) is counted on the sales side. An explicit positive sales marker would avoid the cross-attribution; the funnels are dashboard analytics so the blast radius is a wrong count, not wrong money.

### RBAC surfaces preserve the trust boundary

The dual-view layer is composition on top of the existing matrix, not a new authorization path: `ROLE_SURFACES` maps roles to `entri`/`executive`, mutations remain gated by `can()`, the saveDB net, and firestore.rules, and the change adds no new mutating collection (weighing rides on `goodsReceipts`, PIs on `purchaseInvoices`, both already mapped), so the trust boundary is unchanged. The dual-view test asserts data-entry roles are gated *out* of the executive surface and that an inactive account resolves to no surfaces, so a mapping regression would fail. `ENTRI_ACTIONS` is a single source of truth shared between `rbac.js`, `entri-harian.js`, and the test, keeping "exactly the four operational tasks" from drifting.

### Classic-bundle wiring and Entri Harian hand-off

All four new files are registered in `classicAll` after their dependencies (`sales-purchase-extras.js`) and before `menu-router.js`/`rbac.js`/`lazy-views.js`, so routing and gating see them. Each is a single-`window.X` IIFE with no top-level globals, matching the layer's redeclaration constraint, and the build confirms the concatenated bundle emits without collision. Entri Harian routes its four tasks by synthesizing a hidden `data-action` button click so the existing `addPO`/`addDO` create handlers run unchanged, and delegates Timbangan and Biaya to `_pipelineExtras.openReconciliation` and `_bankExtras.openOtherPayment` — both verified to exist — with graceful toasts if a module is absent. This avoids duplicating create logic at the cost of depending on the delegated-click handler contract, which is the established pattern in this codebase.

### Deferred scope

Section 2's pluggable ingestion is a real contract: `registerRecapSource({id,label,fetchRecaps})` with a shipped `upload` source, a rejected-invalid-source test, and a documented mailbox adapter that reuses `parseRecapWorkbook` — no live provider, as required. Section 4 is a readiness comment over `getVatInvoices()` naming the fields a future Coretax exporter would map, with no serializer, matching the "data-structuring + doc note only" boundary. The demo seed and Indonesian how-it-works guide are present and carry no self-attribution; the diff and commit bodies are clean of AI/agent credits (the only matches are the findings text describing the attribution scan itself, and the environment-set git author identity, which is out of scope).
